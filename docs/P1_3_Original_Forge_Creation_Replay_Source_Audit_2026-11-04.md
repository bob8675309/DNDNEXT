**New source-derived replay concern requiring a disposable test, not an observed production incident:** v3 does not return immediately after v2's existing-character replay. After `v_character_id := public.create_player_character_v2(p_payload, v_proxy)`, its `DELETE` filters spells tagged `shared_character_forge_player_v2`, and its later `INSERT ... ON CONFLICT ... DO UPDATE` can update/append v3 spell assignments. Reusing one request ID with changed (but individually valid) `p_magic_selections` therefore has a credible path to mutate an existing character's spell assignments, even if no extra character/event is created. Do not label the v3 API fully replay-idempotent based only on v2's early return or the reduced V19–V23 trigger tests. A design decision is needed on immutable creation-intent matching versus rejecting altered retries; no production patch is authorized by this observation.

## Trigger and privilege surface actually present live

- `public.characters`: **6** non-internal triggers. No `characters_capture_creator_at_insert_v1` trigger installed. Candidate creator capture is an **unapplied** `AFTER INSERT` addition from #321; it must preserve existing sprite, portrait, movement/location guard and delete protection behavior.
- `public.character_sheets`: **4** non-internal triggers, including authority-field guard, player-tag sync, deferred starting-equipment validation, and sheet-to-progression sync.

- Authenticated table-level `INSERT` on `public.characters` exists but RLS permits it only via Admin check; anonymous `INSERT` is not granted. The four original public creation RPCs are executable by authenticated, not anon, according to live `has_function_privilege`. Candidate creator attribution uses validated `auth.uid()`, never a client-supplied creator ID.
- No new research-only Profile/creator-attribution tables or RPCs were installed live; production still has `can_edit`, `can_inventory`, `can_convert` only.

## Proposed executable acceptance cases (ALL **UNTESTED HERE**)

1. **FCR-01 — Original Admin NPC creation:** Genuine signed-in GM calls the exact original `create_character_v1` through local PostgREST with the proposed creator `AFTER INSERT` trigger. Assert one canonical character and sheet, one immutable attribution to the actual GM, no player-created event, no unintended player grant, and current Profile/portrait/sprite contracts unchanged.
2. **FCR-02 — Original player v2 creation:** Genuine signed-in player calls original v2 under all locally reproduced permissions, class/source catalogues, sheet, progression/starting-equipment triggers and constraints. Assert canonical character/sheet, expected grant and progression, a single `player_character_created` event, source-owned equipment/currency and correct immutable creator.
3. **FCR-03 — Original player v3 creation:** Genuine signed-in player calls exact v3→v2 with valid source-qualified starting magic; verify v2 placeholder replacement, final spell provenance, grants/level-event and no duplicate spell authority.
4. **FCR-04 — Equal-payload retry:** Repeat the same signed-in request ID and same valid payload against v2 **and** v3; check row/event/grant/gear/currency counts and compare complete spell assignments, `updated_at`, and other effects, not merely returned character ID.
5. **FCR-05 — Changed-payload retry:** Reuse the ID with different still-valid starting magic/character details. Prove exact existing behavior, including potential v3 spell addition/update; do **not** claim a safe immutable request envelope until the server rejects or precisely binds mismatched intent.
6. **FCR-06 — Cross-user / revoked editor:** Second valid JWT cannot replay first user's request ID or claim creator attribution; assess behavior when original creator has lost `can_edit` and must not disclose private profile/backstory.
7. **FCR-07 — Invalid creation and transaction rollback:** Use invalid class/source/magic or deferred materializer validation. Failed transaction must leave no character, attribution, event, grants, generated inventory, currency or partial spell assignments.
8. **FCR-08 — Multi-character and legacy snapshot:** Create a second alternate for one user; test current original v2 snapshot replacement as a clearly identified unsafe baseline, then separately test held one-clause #319 correction without changing canonical sheets or account ownership.
9. **FCR-09 — Privilege and visibility:** GM, creator, co-editor, inventory-only, outsider and anon real GoTrue/PostgREST checks; only original creator with active `can_edit` and GM may read creator-authored backstory in candidate #321. Player-facing safe Profile and GM-only secret rules remain independent from full-sheet ownership.
10. **FCR-10 — Concurrent retry and lock-class interactions:** Same-ID two-session creation, full deferred progression/gear triggers, CP↔CS lock-order observation, and cross-character resource independence. Record the actual call that is reachable under signed-in authorization; no artificial prelock is proof of live exploit reachability.
