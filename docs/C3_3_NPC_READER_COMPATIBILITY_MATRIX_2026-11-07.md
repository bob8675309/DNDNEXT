## Current production and staged policy

- Production RLS is on for `characters` and `character_sheets`; `character_sheets_select_visible_or_assigned` currently permits a sheet when the related character row is visible. Stage1 candidate requires `private.can_access_character_v1(character_id,'edit')` for raw JSON sheet SELECT.
- Direct `characters.secret` SELECT is already denied, but previous legacy `SECURITY DEFINER` APIs can serialize sensitive data. Stage3 candidates replace the identified unsafe `get_my_player_character_v1`, `get_my_player_characters_v2`, `get_character_secrets_v1` and `set_character_secret_v1` paths. Preserve independent server authorization, not client-side checks alone.
- Stage2 revokes SELECT on `background,motivation,quirk,mannerism,voice` **role-wide** from `authenticated`. PR #345 adds `get_character_editor_narrative_v1`, authenticated `can_edit`-gated and excluding GM Secrets; it also has a separate Admin-only dossier RPC. These are not installed on DnDWeb.
- A visible NPC's player-safe Profile is not permission to fetch `character_sheets.sheet`. `can_inventory` and `can_convert` must NOT become `can_edit`; creator-authored private backstory remains creator+current-edit or GM, not every co-editor.

## Indirect SECURITY DEFINER audit (live, read-only)

`pg_proc` metadata was scanned for public authenticated-callable JSON/record serializers referencing `character_sheets` or `to_jsonb(c)`. The **known unsafe pre-stage** broad serializers `get_my_player_character_v1` and `get_my_player_characters_v2` return full character/sheet JSON; stage3 covers both, and local signed V00/V09 negative baselines preserve why replacement is necessary. The existing GM secret RPC pair is separately covered. Inspected other candidate functions include `encounter_spellcasting_profile_v1` (checks controller), `get_character_invocation_recovery_v1` and `recover_character_invocations_v1` (gate with `private.can_manage_character_progression_v1`), equipped combat snapshots, feature configuration and level-up APIs. The source scan is **not proof that each server function's returned object has passed the final multi-user signed matrix**; this must remain an explicit acceptance item.
