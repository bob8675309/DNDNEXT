## Binding owner decision

A `creation_request_id` is an immutable identity for the **original complete character-creation intent**, not a mutable character identifier. Repeating that ID with the **same** submitted character, class, spell choices and starting magic returns the original character without rewriting its spells or other data. Repeating the ID with **different** submissions is rejected and the user must start a **new creation request**. A changed nonce cannot be used to edit an existing character. Private data must stay server-confidential.

This decision was explicitly confirmed by the owner in the successor development conversation. It is distinct from tactical command replay R1/R2, yet shares the fail-closed principle. For this first implementation only **player v2 and v3** are wrapped. Original `create_character_v1` Admin/merchant/NPC and historical single-character player v1 remain unchanged and need separate review before claiming a universal creation API rule.

## Source and implementation design

Verified live DnDWeb function MD5 hashes (read-only): `create_player_character_v2` `0351f0a00acae023278e1b8b065b00c9`; `create_player_character_v3` `6ba73e6f12fcf826cc0a739cce45ff40`; `create_character_v1` `b58311c817d8648ef75ae35b66d831c5`. Staged SQL **must fail on source drift** and keeps the original class/spell/permission business-function bodies in private SECURITY DEFINER copies. The private v2 copy makes **exactly one intentional extra change**: the already researched [PR #319](https://github.com/bob8675309/DNDNEXT/pull/319) `players.sheet` conflict-update guard, leaving populated account-level legacy snapshots alone. Its original production snapshot remains unmodified in test fixtures. The private v3 copy is exact except for its internal v2 dispatch. The v3 original's sole nested call to `public.create_player_character_v2` is rewired to the private original v2 so the one original v3 intent remains authoritative.

One private deny-direct-access `player_creation_intent_reservations_v1` table holds the request UUID, authenticated caller UUID, creation API version, **SHA-256 of the original canonical JSONB payload + choices**, canonical result UUID and timestamps. **No duplicate raw sheet, secrets, or spell input** is stored. Its unique request ID and `INSERT ... ON CONFLICT DO NOTHING` serialize same-ID callers: the second caller waits for the first transaction and sees the committed typed intent, owner, and result. The server rechecks current `character_permissions.can_edit` on cached replay. Historical rows created before this candidate have no trustworthy intent fingerprint: replays with such IDs fail closed and ask for a new request ID, without altering the old character.

The public v2/v3 wrappers validate the original nonce and intent **before** dispatch. Identical successful replay returns immediately without entering either original mutation body. Changed payload, changed p_spell_choices, changed p_magic_selections, or cross-API reuse is rejected with SQLSTATE 22023; cross-account/revoked editor with 42501; unprovable historic nonce with 55000. New creation remains atomic with reservation and final result in a **single** database transaction. All original v2/v3 public signatures and existing RPC privileges are preserved. The private original functions and reservation helpers explicitly revoke PUBLIC/anon/authenticated direct EXECUTE.

**Candidate:** `sql/candidates/20261105_player_creation_immutable_intent_v1.sql` (unapplied), not a numbered Supabase migration. This does not rewrite Character Forge UI, starting-equipment resolution, class/casting rules, player profile, or world/town maps.
