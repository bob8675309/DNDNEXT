## 3. Why character-owner INSERT is a separate security boundary

The original checked-in `sql/20260614_02_phase_a_non_map_security_hardening.sql` defines `inventory_items_insert_owner_or_admin` using `user_id=auth.uid() OR private.current_user_is_admin()`; it does **not** validate whether `owner_type='character'` / `owner_id` belongs to that signed-in account or whether the caller may mint inventory for that particular character.

P16's disposable `private.c34_b14_p16_guard_direct_inventory_dml_v1` checks `TG_OP='INSERT'` only for `owner_type IN ('npc','merchant')`. The same P16 signed fixture positively asserted direct browser INSERT for `owner_type='character'` and the current actor's own `user_id`. **Static witness:** the candidate appears to allow a signed actor to create an unearned row with `owner_id` set to an unrelated Forge character, while retaining `user_id=auth.uid()`; whether the specific attack succeeds under real JWT is the P17 signed negative-control question.

The additive signed research module `scripts/integration/c34/run_t46_p3_p4b_c2b14_p17_character_owner_spoof_red_signed.mjs` is called only from the original local-guarded P16 test **after** all P16 legitimate account/Town/Forge/GM INSERT-positive assertions. It creates a foreign `kind='npc'`, `tags=['player-character']` character and assigns its management grant to the unrelated signed OUTSIDER, confirms signed OWNER has **no** character grant, then attempts browser INSERT with `owner_type='character'`, `owner_id=foreign_character`, `user_id=OWNER.uid`. It checks the exact returned owner/account IDs and removes the scratch item, permission and character. The test **expects the existing bad behavior**; green of that test does not mean the security flaw is repaired. At this dossier's initial authoring, the additional genuine signed CI result is **PENDING**; do not promote it to accepted before examining the complete run.

## 4. Compatibility matrix and prospective repair constraints

| Writer / consumer | Legitimate behavior to preserve | Security/compatibility requirement |
| --- | --- | --- |
| Source-original Forge v2/v3 deferred equipment and starting market | Authoritative creation of equipment owned by the newly created character | Validate trusted server context/immutable request/creation provenance; never let arbitrary Data API direct INSERT mint gear for a foreign character |
| `AssignItemButton.js` GM catalogue assignment | Administrative player/NPC/merchant item creation | Verify admin/gm/dm **trusted server role**, actual intended owner and historical `user_id` behavior; this browser currently directly INSERTs, so blanket INSERT REVOKE breaks it |
| Town crafting `pages/town/[id].js` | Account-owned craft result, consumption and rollback INSERT | Maintain account self-owned item creation and atomicity; a self-owned `user_id` is not sufficient proof for a **character-owned** new item |
| `pages/inventory.js` and NPC/Town copied panels | Equip, deletion and user-initiated transfers | Permit allowed equip fields; remove legacy owner UPDATE and generic transfer fallback only with coordinated typed consent + browser replacement |
| Merchant stocks and purchases | Separate stock CRUD, guarded purchase, wallet and reroll | Never route `character_stock` through NPC private backpack consent; source-controlled functions and role guards remain independent |
| Player-to-player trade | `trade_requests` and `accept_trade` | Do not remove independent trade service or silently recast as NPC gift |
| Source-definer inventory writers and trigger/materializer families | Creation, manager assignment, crafting and authorized transfer | Live installed function bodies, invoker/definer context, grants, policies and all indirect invocations require authorized verification; static census is not an execution proof |

A potential P18-compatible direction is to distinguish a **trusted server-issued item-creation intent** from raw Data API character-owner INSERT, then separately preserve genuine Forge/materializers and GM assignment with a local role matrix. Any new guard must be scoped to original source/auth contracts and tested against already accepted P16 positives and old REDs.
