## Versioned P5 contract and accepted test

Files on held research branch only:

- `scripts/integration/c34/candidates/t46_p3_p4b_c2b14_p5_quest_item_intent_contract.mjs`: pure, side-effect-free typed **proposal** helper. Two explicit intents:
  - `send`: one **existing inventory row UUID** and a typed counterparty (`player`, `npc`, `merchant`), optionally a text `questId`. The helper does not transfer anything or assert authorization.
  - `request`: a catalog key plus quantity 1–99, and the counterparty receiving the **request message**. A request proposal does not identify or transfer another person's item row. The eventual NPC delivery target must be derived by trusted server rules, not claimed in an untrusted client proposal.
- Strict input allowlists reject forged issuer NPC, actor user, GM role, `can_control`, `autoAccept`, `questStatus`, `transferReceiptId` and unknown fields; reject character scope as a counterparty wire type. Reject malformed UUIDs, bad catalog key and quantity, control-character quest IDs and client-defined fulfillment. Returned proposals have `state='proposed',mutationAuthorized=false`, never `pending`/fulfilled just because the UI built an object.
- `planQuestItemRequestDecision` yields a **requested** `accept/decline/cancel` proposal only from an existing server `pending` status. It always sets `nextStatus=null` and `requiresServerSettlement=true`, never fabricates a transfer receipt or claims quest completion.

## Future server-side settlement contract (DESIGN ONLY; no SQL candidate)

1. **Visible proposal → pending request**: future backend verifies real signed user, controller, NPC ownership/visibility, quest activity/authorization and source narrative trigger. It creates an immutable, versioned pending request under a **unique request UUID/idempotency key**. Never trust client-supplied `actor_user_id`, `quest_status`, hidden metadata or GM privileges. NPCs may request delivery, accept offered goods or offer rewards; each scenario has independent permissions and visibility.
2. **No inventory movement on a request**: NPC asks for an item; player may acquire it later; requesting does not select someone else's private inventory UUID or claim an existing item.
3. **Accept/fulfill atomically**: a distinct trusted RPC locks the request row, exact inventory row(s), source owner and current applicable NPC/character permission rows in coordinated order; checks player consent, quest objective, actual current owner, catalog/materialization provenance and quantity. Commit exactly once: item transfer/split, unequip, request `fulfilled`, transfer receipt and quest progression. If any step fails, rollback every step. Decline/cancel/expiry never changes item ownership. Parallel accept/replay with same requestId returns the original authorized receipt or fails closed; no duplicated rewards.
4. **Rewards**: an NPC quest reward is either a transfer of legitimately held NPC stock/gear under an authorized server action, or a separate source-validated item materialization; it must never use client-supplied claims to mint arbitrary inventory rows. Preserve merchant stock/economy/currency checkout authority and crafting.
5. **Quest visibility and data efficiency**: expose only permitted NPC and player request summaries plus pending counts/available decisions. Do not expose NPC hidden tags, GM secrets, full Sheet, unrelated players' rows, or narrative spoilers. Keep paginated inventory rows separate. Potentially extend one-RPC B14-P3 context with permitted `itemInteractionActions` and visible pending-request summary when the actual quest module is approved, rather than client recomputing role/targets.
6. **Trade backward compatibility**: existing `trade_requests` keeps player↔player semantics and `accept_trade`; new NPC/quest request ledger should be a **separate future table** or a versioned service-level abstraction. Do not introduce an open client UPDATE status API that can mark request `fulfilled` without moving the item.
7. **Source-specific scopes**: `quest_id` is text; `characters.id`/inventory row UUID; `locations.id` bigint. Do not conflate them. An NPC controller with `can_control` has no automatic right to browse, equip, sell or withdraw that NPC's items. Owner rejects transfers between PCs on the same account even when a PC is `kind='npc'` in Forge.
