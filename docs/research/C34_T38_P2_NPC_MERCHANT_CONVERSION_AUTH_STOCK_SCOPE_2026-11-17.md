## Read-only verified *hosted* source evidence (NO write, function call or data mutation)

- Live Supabase DnDWeb PostgreSQL 17 read-only `pg_get_functiondef` of `public.set_character_kind(uuid,text)`: md5 `04588d4b433b13c92e612039a7c7e56e`, SECURITY DEFINER with pinned search_path, EXECUTE granted to authenticated, not anon. Function checks `auth.uid() IS NOT NULL`, reads `public.user_profiles.role`, and denies only role `player` (after coalesce). **It does not explicitly require one of Admin/GM/DM, does not check subject `can_convert`, does not check kind/existence before stock deletion, and deletes all `public.character_stock` for that ID before updating kind**. Every authenticated actor whose database role text is not `player` may therefore pass the code's role condition if such an account exists. This is a **source-verified risk**, not a live attack or demonstrated exploitation.
- Live `public.convert_character_type(uuid,text)` is a SECURITY DEFINER alias (md5 `1a6ab5aa4bc58eceace51ad3803ed961`), EXECUTE to authenticated, not anon, simply calls `set_character_kind`. A fix must preserve the alias and its forwarded authorization semantics; fixing the wrapper alone is insufficient.
- Live `private.can_access_character_v1(uuid,text)` md5 `97b5e6b059e6467e24c4283fe420c83e` returns manager or a matching delegation; for `'convert'` it currently accepts **`can_convert OR can_edit`**. This does **not** match source-original `pages/npcs.js` UI permission `canConvertKind = isAdmin || selectedCharPerm.can_convert`; preserve separated editor-only and convert-only rights in any proposed replacement after owner review.
- Live `private.current_user_is_admin()` md5 `1fc5fbcb121b2862eeab869edfb3a209` currently recognizes only role `admin`. **Research-only T31** scratch SQL expands *in-game* Admin/GM/DM equally; do not confuse this with hosted state or technical site administrator rights.
- Live `characters` has RLS with UPDATE policy `private.can_access_character_v1(id,'edit')`. Live `authenticated` lacks table-wide UPDATE but has column-level UPDATE on `characters.kind` and `storefront_enabled`. Original `pages/npcs.js` KindPicker first calls `set_character_kind`, then falls back on direct `characters.update({kind,storefront_enabled,updated_at})` if RPC errors. **Potential mismatch:** editor-only actors might be able to update kind by direct DML without `can_convert`; conversion fallback does not wipe stock as the original RPC does. No live write was attempted to demonstrate this; require signed-local proof.
- Original RPC semantics: NPC→merchant enables storefront; merchant→NPC disables storefront and clears six storefront customization fields; stock is wiped on **any** call including an unchanged target. Existing original UI prevents selecting same target, but server API can be called directly. Any adjustment must retain required storefront and original stock semantics for actual changes, while defining safe repeated/no-op behavior explicitly.
