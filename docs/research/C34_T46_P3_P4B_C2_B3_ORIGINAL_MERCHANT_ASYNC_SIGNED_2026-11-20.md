## Why this test is necessary

The accepted C2-B2 result [Actions #44855620965](https://github.com/bob8675309/DNDNEXT/actions/runs/44855620965) reproduced an original `buy_from_merchant` visibility bypass and proved a local guarded SQL candidate for hidden/disabled merchants. It did not run the guarded buyer through real storefront Chromium **after** the guard was installed, nor prove logout/account-switch asynchronous safety. The existing original T28-P1 signed browser [#43740525687](https://github.com/bob8675309/DNDNEXT/actions/runs/43740525687) reproduced late signed stock/wallet display in a deliberately persistent original component, but used a different fixture. T28-P2 guarded component research is not the current original app.

The unchanged **original source blobs** are `components/MerchantPanel.js` `22e4d0810603bc0322904573cb5fe0c14bad1f88`, `utils/useWallet.js` `f34b99f1d6eee66420d57bdcefdc6d3427092e25`, and protected `components/MapPageClient.js` `61f8738da2ca3d8635b5a413bfdc18c094228a0a`. The original `handleBuy` awaits `buy_from_merchant` then `Promise.all([fetchStock(),refreshWallet()])` before reporting success; a successful server purchase with failed refresh enters the same error catch. Original `fetchStock` and `useWallet.refresh` have no actor-epoch validation. These are source findings, not claims of deployed exploitation.
