## Why this is distinct from T28-P0 and P1

T28-P0 uses `createNonMapActorEpochCandidate()` to scope stock by authenticated actor **and** merchant and wallet by actor. T28-P1 mounted the exact-original `MerchantPanel` and `useWallet` across a deliberately persistent scratch logout and held genuine local signed stock and GP responses. Original old bytes were rendered (expected negative); a separate ticketed scratch lane rejected them. Neither test changed the product.

The original `utils/useWallet.js` also takes an optional `userId`: an authorized Admin may request a **different target user's wallet without switching their own authentication identity**. Wallet actor epoch alone therefore cannot detect a same-Admin switch between target A and B. The original merchant's fetch also may have multiple same-actor/same-merchant overlapping reloads (purchase, restock, manual fetch).

## Follow-up source review: numeric leakage through wallet_set return (corrected in research)

**New P2 guard issue found:** Earlier `useWalletT28P2Research.set()` invalidated a stale server response before calling `setGp`, but still returned the full `{data,error}` object from `wallet_set` to its caller. A caller could display an old wallet number after logout or an Admin switch to a different target, despite the hook's state guard. This is a research-only candidate defect, **not evidence that the unchanged production hook or current UI was mounted in the same way**.

**Correction:** The isolated derived hook now compares actor identity, actor epoch, wallet target and target epoch **both before and after** authoritative `wallet_get` reconciliation. If the scope changed, `set()` returns `{data:null,error:Error("Wallet context changed; verify the transaction status before retrying.")}` — never the previous numeric balance. The message explicitly says the **server may already have committed** and prevents blindly treating the browser's rejected callback as a transaction rollback. The mounted `WalletPane` independently tracks `uid` + selected `targetId` and blocks `refresh()/set()` promise callback output on account/target changes.

**Deterministic source-backed proof:** `scripts/integration/c34/test_t28_p2_wallet_set_stale_unit.mjs` uses Node's `vm` and injected React hook/state + Supabase RPC scheduling to evaluate the **actual derived hook source**: R01 late signed-out accepted wallet_set returns no numeric data; R02 same-Admin target A→B suppresses old numeric data; R03 current authenticated set preserves original `{data,error}` API and re-fetches authoritative balance. The three cases were also evaluated successfully in a separate V8 source harness using GitHub-returned current files. **Full GitHub Node22 source CI remains unverified**.

**Signed P2 runner expanded:** After source-original buyer rollback/late-success checks, GM signs back in with 42 GP; a **real local signed wallet_set HTTP 200** is held after server updates GP to 66, then browser signs out before bytes are delivered. It requires `PASS T28-P2-SET-LATE`: no GP or `SET 66` in mounted caller, while ephemeral server balance remains 66. This assertion is **authored, NOT yet shown passing in a genuine Chromium/PostgREST run**.

**More source-test fidelity:** The generated P2 temporary Next route now gets `alternateWalletUserId = users.OUTSIDER.id` from actual disposable GoTrue signup rather than a fabricated never-created UUID; the Admin target transition therefore queries the genuine outsider's 0-GP wallet. ## Sixth increment — stop falsely reporting an accepted purchase as failed

**Concrete bug in the original source:** `components/MerchantPanel.js` calls `buy_from_merchant` and, after the RPC successfully commits, awaits `Promise.all([fetchStock(), refreshWallet()])` inside the same purchase `try/catch`. If the wallet read rejects, the original component displays an error notice even though the player has actually been charged and the item awarded. Repeating the purchase can cause a second legitimate debit. This is a source-derived failure mode, not evidence that the particular production transaction occurred.

**Research candidate change:** The isolated `components/c34/MerchantPanelT28P2Research.jsx` now uses `Promise.allSettled` for *post-commit* stock/wallet refresh. A wallet refresh error shows the successful purchase notice together with a balance-refresh warning, not a failed-transaction message. A current scoped stock read error clears the cached stock list and shows a reopen-shop warning, preventing display of a stale purchasable shelf. Genuine buyer-RPC errors continue to produce an error notice; late responses from an earlier account/merchant remain suppressed. The buyer RPC signature, fallback, inventory semantics and original shared product files are unchanged.

**Actual-function original RED / guarded GREEN:** Added `scripts/integration/c34/test_t28_p2_purchase_refresh_unit.mjs`, which extracts and *executes* `handleBuy(card)` directly from both the byte-pinned original production `MerchantPanel.js` and the isolated research copy with deferred/scoped RPC mocks. Expected original RED: accepted buyer response followed by rejected `wallet_get` produces a false failure notice. Guarded GREEN: R01 accepted buyer/failed wallet read retains success; R02 buyer RPC truly fails; R03 post-logout accepted response is silent; R04 merchant-switch response is silent; R05 normal success remains unchanged; R06 failed post-commit stock refresh retains successful notice with warning. All actual-function cases were executed in an isolated V8 harness against live GitHub-fetched current sources and PASS. Both C34 workflows now execute this regression. The derived source contract also pins the new stock/error logic and original RED/R01–R06 markers and passed over 16 fetched current source files.

## Seventh increment — synchronous single-purchase lock across React render and merchant switches

**Issue:** The original and initial T28-P2 merchant purchase path used React `busyId` state to disable the Buy action, but state updates do not synchronously serialize two calls arriving before the next render. Both could issue independent `buy_from_merchant` RPCs. The authenticated server transaction is atomic *per call*, but that is not equivalent to deduplicating two separately accepted buyer requests.

**Research correction:** `components/c34/MerchantPanelT28P2Research.jsx` now keeps `purchaseInFlightRef` and builds a synchronous purchase key from captured `actorId`, `actorEpoch`, `merchantId` and `merchantEpoch`. It first requires current guard scope to match BOTH the current hook `uid` and selected `merchant?.id`; it then rejects another Buy call for the same account/merchant generation before sending a second RPC. A new merchant/actor generation can purchase independently without waiting for the old request. The old request's `finally` clears the ref **only if it still owns that exact token**, so it cannot unlock the new merchant's request. Existing `busyId` still controls button visuals; original world-map/shared merchant and wallet remain unchanged.

**Direct handler tests:** `scripts/integration/c34/test_t28_p2_purchase_refresh_unit.mjs` now includes R07 (two same-render Buy calls produce exactly ONE original buyer RPC, lock released after resolution) and R08 (old pending merchant request neither blocks a new merchant's purchase nor clears its active lock). Updated `test_t28_p2_derived_source_contract.mjs` pins actor/merchant props, token ownership and new R07/R08 markers; independently executed over 16 current GitHub source files PASS.
