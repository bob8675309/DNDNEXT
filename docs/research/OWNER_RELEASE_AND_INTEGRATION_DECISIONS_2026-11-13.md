3. **Historical data may be removed when genuinely obsolete:** Conditional yes. This is **not** a blanket DELETE or authorization to destroy provenance. First identify owner/use, canonical references, RLS/permissions, saved character/GM meaning, historical/audit uses, conversion dependencies, and exact proposed rows. Produce a dry-run deletion manifest with source/row counts and rollback/restore proof. Distinguish legitimate but historical data from abandoned test/scratch/duplicate data. Never infer a record's lack of value from `granted_by IS NULL`, age, or a superseding schema alone. No production destructive SQL until the specific deletion set and production change are separately approved through the release gate.
4. **Full real-browser acceptance before the first production merge:** Yes. Cover the real Forge ten-step player creation and source-valid species/class/feats/spells/equipment; alternate and GM/NPC creation; multi-account identity; immutable nonce create/replay; GM vs private Story, sanitized NPC Profile and GM-only secrets; town/world Profile click contract and merchant storefront; inventory ownership/trades, sheets, print and relevant migrations. Use at least Admin, real creator, co-editor, inventory-only, outsider, unauthenticated, and revoked-role sessions, including negative cases. Test real signed Auth and current browser routes; fixture-only static CI is not a substitute. Preserve world/town/tactical map separation. Do not change protected world-map behavior without a prior discussion.
5. **Independently verified DB+Storage restoration before production migration:** Yes. The historical capture receipt is **PG17 custom dump 16,704,002 bytes; 340 Storage objects in four buckets, 453,153,680 bytes**. A capture and manifest are **not** a verified restoration. Check the encrypted protected secondary copy and execute an isolated independent restore of DB **and** Storage, verify byte/hash manifests, permissions and real reads; rehearse safe migration/rollback against restored data. Gate any production SQL/data changes and any main merge that would deploy incompatible runtime on this proof.
6. **Most efficient route without sacrificing data integrity:** Yes. Reuse unchanged original source, existing proven 2024 logic/19 tactical spell adapters, signed tests and evidence. Group compatible unresolved triggers into **dependency-coherent vertical slices**, run targeted fail-closed tests during development, then full T1–Tn and original source CI at each executable acceptance head. Avoid repeatedly rebuilding fixtures and avoid a giant PR with unrelated release gates. Prioritize highest-risk compatibility, source-auth and data-integrity blockers first. Parallelizable **read-only** source audits and browser test preparation may advance without waiting on a production restore; actual deployment/data edits may not.
