## Source evidence: exact lock sequence and functional boundaries

Verified current original `components/MerchantPanel.js` blob `22e4d0810603bc0322904573cb5fe0c14bad1f88`, original captured DnDWeb `public.buy_from_merchant(uuid,uuid,integer)` definition in `scripts/fixtures/forge_original_merchant_buy_source_pg17.sql` blob `72fd9f0f80a83adaec67caf80a762e238f1dcd8c` (historical function md5 `1dbe8c24c4c718396d7256f6f7465354`), and C2-B2 test-only source guard blob `bde3cb3bd79a20fa2777a902c8e091d591d56f28`. Do **not** assert hosted SQL implementation parity; this is a captured function and disposable signed test.

1. Guard preface performs `SELECT` of **same seller** `public.characters` with `FOR SHARE` before all original statements, restricting kind='merchant', `is_hidden IS NOT TRUE`, `storefront_enabled IS TRUE`, and throws `42501` otherwise. **No condition on state, home_location_id, location_id, moving, camping or travel**. The original buyer then locks one `character_stock` row `FOR UPDATE`, checks recipe/quantity, ensures and locks the **buyer wallet** `FOR UPDATE`, debits once (unless -1GP), decrements/deletes the stock, then delivers inventory or a recipe unlock within the same PostgreSQL function transaction. The seller SHARE lock permits multiple buyer sessions to hold merchant visibility concurrently, but both serialize on the same stock row; an UPDATE/DELETE to seller may block behind the seller SHARE lock.
2. Original `MerchantPanel.changeQty` issues `from('character_stock').update({ qty }).eq('id', stockId)`, where `incQty` calculates `(row.qty||0)+by` from the **already rendered stock array** rather than server-current quantity. This is an absolute client-side read/modify/write without a version compare or atomic increment, and can overwrite a post-purchase decrement even if row locks prevent simultaneous writes.
3. Original manager `removeRow` and `dump` issue direct `character_stock DELETE`; the emergency reroll fallback deletes stock and subsequently inserts replacement rows in a **separate HTTP request**, not one atomic stock-swap transaction. Its primary `reroll_merchant_inventory_v2` is a separate server RPC: the original source of that hosted procedure and its lock order have **not** been certified by this dossier. Do not infer the reroll RPC uses the fallback's order or that a real simultaneous manager seller UPDATE occurs in the same transaction.
4. The manager's original `stock_merchant_item` is a separate RPC. Historical `docs/Cron INFO important.txt` includes an older single `INSERT character_stock` procedure excerpt, but that archival excerpt and presently deployed function cannot be equated without a fresh source-actual MD5/definition check. The current frontend additionally falls back from **any RPC error** to a direct stock INSERT, another source-derived behavior requiring later independent privilege and idempotency review.

After commit, buyer must encounter B2 `42501 Merchant unavailable` with stock and inventory unchanged. The seller is returned visible for subsequent tests; no game-route or world-state change.
- **Stale manager quantity:** The original client reads stock quantity 3; a real signed purchase reduces it to 2; a signed DM then issues the *exact frontend-shape absolute PATCH* based on the prior 3 (+1), setting quantity 4 instead of atomic 3. The B2 disposable fixture grants **only a local, role-gated UPDATE(qty) RLS proxy** for this test, explicitly revokes the proxy in unconditional finally, and verifies an outsider cannot use it. This is a characterization of a frontend stale-value conflict, **not a claim that hosted stock manager RLS is identical**.
- **Manager source-shape DELETE wins:** A separate privileged local transaction deletes and holds one stock row; a real signed buyer submitted while delete is uncommitted must fail “Stock not found” after commit, without losing GP or getting inventory. This is an SQL lock-order test, **not a signed manager permission certification**.
