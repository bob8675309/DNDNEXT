# Realistic Dice Roller — Architecture, Runtime Status, and Future Roadmap

Updated: 2026-09-15

Status: **Phase-1 reusable dice core and Character Forge adapter are implemented on `main`; Character Sheet and tactical adapters remain future phases.**

This document supersedes the 2026-08-30 “implementation not started” status. The original Three/R3F/Rapier proposal was useful design exploration, but it is not the architecture that was ultimately merged.

## Current implementation

Merged PR #177 established the reusable dice baseline. Current important paths include:

- `components/dice/RealisticDiceTray.js`;
- `components/dice/RealisticDiceTray.module.css`;
- `components/dice/adapters/ForgeAbilityDiceTray.js`;
- `utils/dice/diceRollContract.js`;
- `utils/dice/diceVisualSeed.js`;
- `utils/dice/physics/dicePhysicsEngine.js`;
- `scripts/validate_realistic_dice_core.mjs`.

The current engine uses a custom deterministic JavaScript simulation and CSS/DOM transforms. It does **not** currently depend on Three, React Three Fiber, Rapier, or `@react-three/rapier`.

`dicePhysicsEngine.js` owns visual simulation concerns such as seeded spawn variation, fixed-step integration, gravity, wall/floor contacts, die-to-die collisions, rotational settling, dragging/repositioning, and final low-energy face guidance. `RealisticDiceTray.js` renders the visual tray/dice, smooths render state, and exposes the reusable consumer surface. `ForgeAbilityDiceTray.js` adapts the existing Character Forge ability-roll objects.

## Locked architecture rule

> **Game rules decide the result. Dice physics only visualizes that already-known result.**

This remains non-negotiable.

The dice layer must never decide or alter:

- attack hit/miss;
- save success/failure;
- damage/healing totals;
- initiative ordering;
- generated ability scores;
- advantage/disadvantage winner selection;
- spell targeting;
- tactical movement/path legality;
- world-map travel/location state.

## Character Forge integration — implemented

The Character Forge remains authoritative for generated ability-score results and allocation. The dice adapter visualizes those generated totals and preserves the existing interaction contract rather than replacing creation math.

Preserve:

- hidden/unrolled initial state;
- six generated totals for rolled methods;
- underlying dice/dropped-die explanation;
- result-cube presentation for aggregate totals;
- click/drag allocation behavior;
- reroll behavior;
- collision-safe manual repositioning within the tray;
- reduced-motion/accessibility behavior;
- separation between mechanical result and visual seed.

A `resultCube` is a presentation type, not a literal d6. It can display aggregate values such as 3–18 because the result was already generated by Forge rules.

## Current physics/presentation principles

### Deterministic visual seed

Mechanical RNG and visual RNG are separate.

- Mechanical RNG produces the rules result.
- A visual seed controls presentation variation such as spawn location, launch velocity, angular velocity, and collision sequence.

A future multiplayer/tactical adapter may use an authoritative command/request ID as visual-seed material, but visual seeding must never become rules RNG.

### Fixed-step simulation

The current custom engine uses high-frequency fixed-step simulation with bounded substeps/collision iterations to keep contacts stable across browser paint rates. Rendering smooths toward simulation state; rendering does not overwrite mechanical outcomes.

### Settling and face guidance

A result must finish visually consistent with the authoritative value. Low-energy guidance/righting may influence final presentation, but it may not change the underlying roll.

### Drag/reposition

After appropriate settling, Forge result dice may be repositioned in the tray without becoming collision-authoritative game pieces. Manual tray movement is visual/UI behavior only.

## Why the original Three/R3F/Rapier plan is now historical

The August roadmap proposed:

- `three`;
- `@react-three/fiber`;
- direct `@dimforge/rapier3d-compat`;
- a WebGL polyhedral engine.

Current `package.json` does not contain those dependencies, and the merged implementation does not use them. Do not add those libraries merely to make old prose true.

A future project may still evaluate WebGL/true-polyhedral rendering if the existing custom engine reaches a concrete limitation, but that would be a deliberate replacement/extension project with browser-performance and accessibility acceptance criteria, not a required “completion” of Phase 1.

## Character Sheet integration — future bounded phase

The shared sheet already has a structured roll/result seam through the sheet component/panel/profile flow. A future `CharacterSheetDiceOverlay` or equivalent should adapt resolved sheet rolls rather than rewriting formulas simply to add animation.

Initial candidate coverage:

- ability checks;
- skills;
- saving throws;
- initiative;
- advantage/disadvantage pairs;
- later damage/healing expressions when explicit die results are available.

Keep the existing textual math/result output. Visual dice supplement it; they do not replace readable result information.

If a later security/multiplayer project moves local sheet RNG server-side, the visualization contract should continue to work because it consumes a resolved result.

## Tactical integration — future bounded phase

Tactical combat is a separate server-authoritative rules system.

Relevant surfaces include:

- `pages/encounters/*`;
- `components/encounter/*`;
- `utils/encounterHex.js`;
- encounter RPCs;
- `encounter_combat_log`;
- request/command identities.

Future tactical dice should animate already-resolved combat-log/RPC results. It must never independently reroll an attack/save/damage result on the client.

An encounter `requestId` or equivalent command identity may be useful as visual-seed input after reproducibility is tested.

## Hard separation from tactical hex physics

Dice contacts and tactical movement solve different problems.

Dice simulation handles continuous presentation values such as position, rotation, velocity, gravity, contact, damping, and settling.

Tactical movement handles discrete game rules such as axial hex coordinates, occupied cells, movement cost, difficult terrain, blockers, reach, LOS, cover, targeting shapes, turns, and actions.

Do not reuse dice collision code to authorize token movement, occupancy, LOS, or pathfinding. A future token animation may interpolate between server-approved hexes, but the server/hex rules decide which hexes are legal.

## World-map boundary

World-map behavior is unrelated to this subsystem. Do not add dice physics/rules to `MapPageClient.js`, travel, routes, weather, camps, or world clock.

If a future world/town interaction wants a roll presentation, use a local/shared dice consumer without giving the world map dice-rule authority.

## Data/storage boundary

The current dice core needs no dedicated Supabase schema. Do not add roll-history/preferences/replay tables without a concrete product requirement.

For tactical multiplayer/replay, prefer consuming already-existing authoritative request/log state before inventing duplicate roll records.

## Validation expectations

Current focused validation includes `scripts/validate_realistic_dice_core.mjs`.

For future changes, validate at minimum:

- normalized roll contract remains consumer-independent;
- authoritative result survives every visual path;
- visual seed does not replace rules RNG;
- Forge allocation/reroll behavior remains intact;
- reduced-motion/fallback paths remain usable;
- manual repositioning does not alter allocation/result authority;
- no tactical/world-map authority crosses into dice physics;
- repeated rolls visibly vary while still converging to the authoritative result;
- no new helper/hook/state/prop/reference is used without being defined and passed.

## Future roadmap

### Phase 1 — COMPLETE BASELINE

- reusable roll/dice contract;
- visual seed support;
- reusable tray;
- custom deterministic physics simulation;
- collision/settling behavior;
- Forge ability adapter;
- focused validation.

Browser tuning may continue when Paul identifies a concrete visual defect, but Phase 1 is no longer “not started.”

### Phase 2 — Character Sheet consumer

Implement only when requested. Reuse resolved sheet results and keep formulas authoritative in their existing layer.

### Phase 3 — damage/healing notation/result enrichment

If current action results do not expose enough per-die detail for meaningful animation, improve the resolved-result contract at the correct authority boundary rather than having the animation reroll independently.

### Phase 4 — tactical consumer

Consume server/RPC/combat-log results. Keep tactical pathing/LOS/turn/action authority separate.

### Phase 5 — global host only if justified

Consider a global dice overlay host only after at least two real consumers demonstrate a need. Do not globally initialize expensive presentation machinery merely because the architecture could support it.

### Optional future renderer replacement

Only if the current custom simulation hits a concrete quality/performance requirement that cannot be reasonably solved, evaluate WebGL/true-polyhedral rendering (including Three/R3F/Rapier or contemporary alternatives) as a separate architectural decision. Re-check current package compatibility at that time.

## Protected boundaries

Dice work does not authorize changes to:

- world-map behavior;
- town/city-map behavior;
- world routes/travel/weather/camps/clock;
- crafting recipes/material/economy authority;
- inventory/equipment authority;
- merchant/storefront systems;
- tactical movement/path/LOS/turn rules;
- unrelated Character Forge choices/persistence;
- Supabase schema unless separately justified.

The durable invariant is simple: **resolve the game result first, then make the dice show it convincingly.**
